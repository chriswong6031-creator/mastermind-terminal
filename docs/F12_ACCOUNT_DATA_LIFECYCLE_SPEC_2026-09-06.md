## 2. Export spec (advances MO-PAID-086, does not close it)

### 2.1 Where it lives

### 2.2 Contract
`GET /api/account/export`, `Authorization: Bearer <supabase access token>` → 200 JSON attachment `mastermind-export-<YYYY-MM-DD>.json`; 401 no/invalid token; 429 one export per 15 min per user (in-memory sliding-window throttle, same pattern as the existing brain burst-throttle, `app/main.py:1223-1250` — a fresh per-endpoint dict, not the brain's own, since a rate-limit collision across unrelated endpoints would be its own bug); 503 `{error, partial:false}` **only when zero collections could be read at all** (e.g. a total backend outage) — **round 3 fix for MINOR 2, which found this line contradicting §2.2/§2.3's own `unavailable[]` contract:** a bundle missing one or more collections is never a 503, it is always 200 with those collections listed in `unavailable[]` (§2.5 test 4); `partial:false` on the 503 path describes "no bundle was produced", not "no collection is missing".

## 3. Deletion spec (advances MO-PAID-087; MO-PAID-078 stays blocked pending 087)

### 3.1 Contract
`POST /api/account/delete`, `Authorization: Bearer <token>`, body `{confirm_email}` → 200 `{ok:true, receipt}`; 400 mismatch; 401 no/invalid token, including a token whose user id no longer exists (round 2 fix — see §3.5 test 9); 409 already in progress (**round 3 fix for MAJOR 4, which found no mechanism behind this code — see §3.2 stage 0 and §3.5 test 12**, backed by a persisted in-flight marker, not a best-effort in-memory guess); 503 `{ok:false, stage, identity_deleted, receipt(partial)}` — `identity_deleted` is `true` only once stage 5 has **completed successfully** (**round 3 fix for MAJOR 2, which found "has run" mapping a stage-5 call that itself errors, times out, or returns non-2xx to the "your account has been deleted" copy — the identity was never actually deleted in that case; see §3.5 test 11**), so the client can pick the correct partial-failure copy in §3.4.

**30-day retention of post-request email_log rows (round-8 fix for BLOCKER 1 — ruling clause A, taken literally):** the build packet implementing this spec adds one new nightly step, `scripts/purge_deletion_receipts.py`, invoked from the existing nightly pipeline (forward-state cleanup, not a live-request action — per this repo's own law the nightly is its sole advancer). The ruling's own text is `created_at < now() - interval '30 days'` **for that to_email** — i.e. scoped to the specific address of the account that requested deletion, never a blanket sweep of every address in the table. **Deleted rather than defended:** round-7's reading of this as license for a "general email_log retention sweep … uniformly, for every address" is removed — it was not a harmless superset. It would also purge every still-active, never-deleted user's `email_log` rows once they turn 30 days old, which (a) contradicts this document's own §2.3 item 3 export-exclusion copy ("Contact support if you need proof a specific email was sent" — false for an active user's older mail under a blanket sweep) and (b) needlessly destroys the `idem_key` unique-constraint row (`0007_support_email.sql:77`) backing every live user's ordinary transactional mail, not just a deleted account's.

The scoping mechanism needs no new table and no new column: `email_log.user_id` carries **no** FK to `auth.users` (§1 row 19, `0007_support_email.sql:80-81`), so once an account is deleted its rows keep the now-orphaned `user_id`, while an active user's rows keep a `user_id` that still resolves in `auth.users`. The job is therefore:
`delete from email_log where created_at < now() - interval '30 days' and user_id is not null and not exists (select 1 from auth.users u where u.id = email_log.user_id)`
— `user_id is not null` excludes sends never tied to any account (out of scope for a per-subject retention rule); the `not exists` clause is true only once the referenced account no longer exists in `auth.users`, i.e. only for a `to_email` whose account has actually been deleted — matching the ruling's "for that to_email" scope exactly, and leaving every active user's delivery ledger untouched indefinitely, not just for 30 days. **This purges `email_log` only** — `account_deletion_receipts` is retained indefinitely by design, keyed solely on `subject_digest`, with no purge job of any kind touching it (MINOR-3). Neither existing index serves this filter — `email_log_to_created` is keyed `(to_email, created_at desc)` and `email_log_template` on `template` alone — so this is a full-table scan with an anti-join against `auth.users` under the current DDL; adding an index is a build-packet concern, out of scope for this records document. Owner: the nightly pipeline. Test: §3.5 test 13 below (rewritten).
Retained on purpose, each disclosed by name in the confirmation copy and matching §3.4's copy exactly: `email_suppression` (#21, address-keyed, covers people who never registered); `ip_geo` (#14, never purged and not disclosed at all in round 1: it is not user-scoped and cannot be safely deleted by any identifier this subject uniquely owns, since IP addresses are shared across households, offices and NATs; deleting by IP would be its own cross-tenant defect, so it is retained and disclosed instead of purged); every `email_log` (#19) row timestamped `created_at >= requested_at` — a timestamp boundary, not an identity match (**round-7 restoration of ruling clause A**, reverting round-6's MAJOR-4 fix) — kept for 30 days and then purged by the new nightly job, scoped to that specific `to_email` once its account no longer exists — never to every address in the table (**round-8 fix for BLOCKER 1**); and the user's `support_tickets`/`support_ticket_messages` rows (#17/18), kept with the account link removed rather than deleted, per stage 8 above (**round-5 fix for MAJOR-4**; `user_id` explicitly nulled, `email` redacted, and `meta` cleared to `'{}'::jsonb` — **round-6 fix for MAJOR-1, round-7 fix for MAJOR-2**). `stripe_events` (#16) is **not** in this disclosed list: **round-5 correction (MAJOR-2)** found it carries no per-subject column at all (§1 item 2 — no FK to `auth.users`, no payload, per `0005_user_entitlements.sql:40-44`), so there is nothing about *this* subject to disclose from it — distinct from Stripe's own external records (#27, §2.3 item 4), which round 2/3 correctly kept separate. Aggregate campaign counters (#22) are deliberately not in this list — they hold no data about *this* subject (§1 point 5: `email_campaigns` has no FK to any user), so they are not this subject's retained data and do not belong in a per-user retention disclosure.

**Why this ordering (round 2 repair for BLOCKER 1):** round 1 moved the explicit purge to run last so it would catch the receipt's own `email_log` write — correct in spirit for `email_log`, which has no FK and so is never touched by stage 5's `on delete set null`, but round 1 through 4 all purged that row along with everything older, which round-5 fixes below. Round 1 also left `support_tickets`, `search_events` and `analytics_events` looked up "for that user" via `user_id` at the final stage, and those three tables *are* FK'd with `on delete set null` (`scripts/deploy/0007_support_email.sql:32` for `support_tickets`; `0003_search_events.sql:43` and `0004_analytics.sql:32` for the other two) — stage 5's own admin-delete already nulls that column for every one of the user's rows before the final stage ever runs, so "`user_id` = this user" resolves to nothing and the purge silently no-ops. The fix is the new stage 4: capture each row's own primary key (ticket id; `search_events`/`analytics_events` row `id`) *before* stage 5 destroys the `user_id` link, and have the final stage act on those captured PKs instead — never on the device/browser identifiers those rows also carry, which round 3 confirmed are not provably single-subject (§1 item 2).

**Round-5 fix for the BLOCKER (email_log purge boundary and the receipt's own home):** rounds 1-4 bounded the `email_log` purge at `created_at <= requested_at` and stated this boundary *includes* the row stage 7 itself writes — but stage 7 (the receipt send) necessarily runs, and therefore its row is necessarily timestamped, *after* `requested_at` was captured at stage 0, so that claim was backwards: `<=` would in practice exclude the row anyway on any real clock, and the stated rationale ("still includes the row stage 7 just wrote") was simply wrong. This document instead makes the exclusion explicit and load-bearing rather than accidental: the boundary is `created_at < requested_at`, strictly before, and the confirmation row is **retained on purpose for 30 days** as the user's own proof that the deletion ran — never silently deleted with the rest of the address's mail history. A consequence, not a coincidence: because stage 8 no longer purges the very row stage 7's send created, that row's own `idem_key` unique-constraint claim (`scripts/deploy/0007_support_email.sql:77` — the DDL that defines the constraint; `app/mailer.py:181-193 _ledger_insert` is the function that hits it, not its source, **round-6 fix for MINOR-5**) survives deletion intact — a resumed/retried run's own send attempt still hits the ordinary duplicate-key protection every other transactional email relies on, with no separate "stored record" fallback needed (simplifying rounds 1-4's reasoning, which needed one only because those rounds' purge boundary destroyed this exact row).

**Round-7 reversion of the round-6 refinement (ruling clause A-restored), round-8 correction of an unsupported claim (MAJOR 2):** round-6 read the round-5 boundary's forward-retention as an undisclosed gap — any transactional mail the run itself triggers after `requested_at` (e.g. a hypothetical billing-cancellation notice from stage 2) would survive unnamed alongside the confirmation row — and closed it by making stage 8 delete every such row except the one matched by its own `idem_key`. The Meta-CEO ruling supersedes that narrower fix: stage 8 goes back to leaving **every** row at/after `requested_at` alone. Round-7 additionally claimed this reopened no disclosure gap because §3.4's copy plus "the nightly job's now-general scope" closed it — that claim does not survive contact with §3.5 test 2, which requires a distinct non-confirmation post-`requested_at` row to remain **present, untouched** after the run, while §3.4's copy names only "the confirmation email record," never any other post-request send. **Deleted rather than defended:** this document no longer claims that gap is closed. In practice no stage in §3.2 sends any email besides stage 7's own confirmation, so a second post-`requested_at` row would only ever come from an unrelated concurrent system send (e.g. a marketing email firing at the same moment) — a real but narrow edge case, out of scope for V1. §3.4's copy discloses the confirmation row by name; the 30-day nightly job (per-`to_email`, deleted-account-only scope — round-8 fix for BLOCKER 1, above) eventually ages out any such row once the account is deleted, whether or not it was separately named in copy.

**Failure posture:** every stage idempotent/re-runnable; a failure at stage n returns 503 with `stage` + `identity_deleted` + partial receipt. A partially deleted account must never be reported as deleted, and a fully deleted identity must never be reported as still active (see §3.4). Stage 5 is the point of no return; stages 6-8 (receipt, notification, non-cascading purge) still run afterward to complete cleanup and notification even though the account is already gone.
