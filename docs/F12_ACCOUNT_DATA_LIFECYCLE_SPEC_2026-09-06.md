## 3. Deletion spec (advances MO-PAID-087; MO-PAID-078 stays blocked pending 087)

### 3.1 Contract
`POST /api/account/delete`, `Authorization: Bearer <token>`, body `{confirm_email}` → 200 `{ok:true, receipt}`; 400 mismatch; 401 no/invalid token, including a token whose user id no longer exists (round 2 fix — see §3.5 test 9); 409 already in progress (**round 3 fix for MAJOR 4, which found no mechanism behind this code — see §3.2 stage 0 and §3.5 test 12**, backed by a persisted in-flight marker, not a best-effort in-memory guess); 503 `{ok:false, stage, identity_deleted, receipt(partial)}` — `identity_deleted` is `true` only once stage 5 has **completed successfully** (**round 3 fix for MAJOR 2, which found "has run" mapping a stage-5 call that itself errors, times out, or returns non-2xx to the "your account has been deleted" copy — the identity was never actually deleted in that case; see §3.5 test 11**), so the client can pick the correct partial-failure copy in §3.4.

### 3.2 Order of operations (load-bearing; round 2 repair below fixes an unreachable-rows defect the round-1 reorder introduced)
0. Verify token→user (`app/main.py:952 require_user`, the same secretless Bearer verification every authed route uses); require a typed `confirm_email` match — this is a new mechanism, no existing typed-confirmation precedent exists anywhere in either repo (grepped both repos for `confirm`; nothing but unrelated prose/comments), so the build packet adds it fresh rather than reusing something that doesn't exist. **Round 3 addition (MAJOR 4 — the 409 mechanism):** once token and email match, compute `subject_digest = sha256(user_id+email)` (the same digest §3.3 stores) and insert an `account_deletion_receipts` row with `status='in_progress'` under a partial unique index on `(subject_digest) where status='in_progress'` (§3.3); a conflicting insert means a run for this account is already in flight, and the request returns 409 immediately, before stage 1 touches anything. This is a persisted database row, not an in-memory guess — unlike the existing brain burst-throttle (`app/main.py:1223-1250`), an in-memory single-process pattern not reused here because a deletion run can legitimately outlive one request/process.
1. Offer (never force) the §2 export first; UI requires a checkbox acknowledgement.
2. Cancel live Stripe subscriptions — reuse `app/billing.py:1470 _cancel_subscriptions` — must precede identity deletion or a charge lands on a vanished account. Sets receipt field `billing_cancelled:true` the instant this stage completes (round 2 repair for MAJOR 2 — this flag, not `identity_deleted`, is what lets §3.4 disclose an irreversible side effect that happened before the point of no return).
3. Delete the filesystem quota ledger for `_safe_uid(user_id)` (`engine/research_vault/download_quota.py:61,91`) — outside Postgres. Sets receipt field `quota_ledger_deleted:true` the instant this stage completes (same round 2 repair as stage 2).

Held only in request-local memory for this call — never persisted, never part of the receipt.

No new secret store, no new auth plane. Cascades tables #1-11,15,20,23,24 *if §4.1/§4.1b confirms it*; also fires the `on delete set null` that clears `user_id` on #12/13/17. **This stage is the point of no return only once the call itself succeeds** (round 3 fix for MAJOR 2) — every later stage is cleanup/notification, not a chance to abort; if this call errors, times out, or returns non-2xx, the response is 503 `stage="delete_identity"`, `identity_deleted:false` (see §3.1, §3.4, §3.5 test 11), because the identity was never actually deleted.

Aggregate campaign counters (#22) are deliberately not in this list — they hold no data about *this* subject (§1 point 5: `email_campaigns` has no FK to any user), so they are not this subject's retained data and do not belong in a per-user retention disclosure.

**Why this ordering (round 2 repair for BLOCKER 1):** round 1 moved the explicit purge to run last so it would catch the receipt's own `email_log` write — correct for `email_log`, which has no FK and so is never touched by stage 5's `on delete set null`. But it left `support_tickets`, `search_events` and `analytics_events` looked up "for that user" via `user_id` at the final stage, and those three tables *are* FK'd with `on delete set null` (`scripts/deploy/0007_support_email.sql:32` for `support_tickets`; `0003_search_events.sql:43` and `0004_analytics.sql:32` for the other two) — stage 5's own admin-delete already nulls that column for every one of the user's rows before the final stage ever runs, so "`user_id` = this user" resolves to nothing and the purge silently no-ops. The fix is the new stage 4: capture each row's own primary key (ticket id; `search_events`/`analytics_events` row `id`) *before* stage 5 destroys the `user_id` link, and have the final stage delete by those captured PKs instead — never by the device/browser identifiers those rows also carry, which round 3 confirmed are not provably single-subject (§1 item 2). `email_log`'s own purge is unaffected — it was never nulled, so matching by `to_email` still works exactly as round 1 designed it.

**Because stage 8 purges the very `email_log` row that stage 7's send created (its `_ledger_insert` idem_key claim included), the receipt's own stored record of whether the notification stage already succeeded — not `app/mailer.py:181-192 _ledger_insert`'s idem_key check — is what a resumed/retried run must consult before calling the mailer again: the guard row that would normally stop a duplicate send is gone by design once stage 8 completes.**

**Failure posture:** every stage idempotent/re-runnable; a failure at stage n returns 503 with `stage` + `identity_deleted` + partial receipt. A partially deleted account must never be reported as deleted, and a fully deleted identity must never be reported as still active (see §3.4). Stage 5 is the point of no return; stages 6-8 (receipt, notification, non-cascading purge) still run afterward to complete cleanup and notification even though the account is already gone.
